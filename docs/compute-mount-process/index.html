Part 1

What it is, and how to use it

Your project's files can stay on your computer while its code runs on Colab's GPU or a GPU server of yours. Before Companion 0.19.0 the code got there as a copy: before each run the changed files were copied over, and after it the results were copied back. With the mount, the GPU machine reads the folder where it is, the way a notebook reads Google Drive once it is mounted. Nothing is copied before a run and nothing is brought back after it.

How it was built, checked and measured, with the step-by-step test plan, is in compute-mount-process.md. Both documents are printed as one PDF, docs/compute-mount-process.pdf (node scripts/compute-mount-pdf.mjs).

This needs Koios Companion 0.19.0 or later on the computer that has the files, and a compute link (compute-link.md).

1. Turning it on

Storage & compute → Sync → Mount the folder on <machine>. The setting is kept with the project. Whenever the machine doesn't have the folder mounted (a new Colab runtime, say), the page starts the mount again. The chip above the terminal reads Mounted on Colab ⇄ live while it is up. From a terminal on the computer with the files:

koios mount            # fuse where the machine allows it, else a live mirror
koios mount --mode mirror
koios unmount          # back to copying before each run
koios status           # says whether it is mounted, and connected

While the folder is mounted, koios run and the page's ▶ Run skip the copy, and Copy now says there is nothing to copy.

So a checkpoint written to checkpoints/model.pt is written at local disk speed on the GPU machine and goes to wherever you keep data. It never crosses the tunnel to your laptop. The rules are the ones under Not copied in the Sync pane, and they mean the same thing they did before.

3. How it reaches your computer

Figure 1. The machine dials out to the nearest Cloudflare edge. Cloudflare carries the connection to the edge nearest your computer, and the Companion's cloudflared hands it on. The browser and the Worker are not on the path, and neither machine accepts a connection from the internet.

  • One socket, kept open. The daemon on the machine (koios_mount.py) holds one WebSocket to /companion/mount/socket on the Companion's tunnel. It doesn't open a connection per file or per run. If the socket drops, the daemon reconnects with backoff, and the Companion sends the tree again on reconnect.
  • The small files first. On connecting, the Companion sends the folder's tree. Every file of 2 MB or less then comes over in a few gzip'd archives (Python files first), so imports and configs are local from the start. Bigger files are fetched in 4 MB pieces the first time they are opened, then kept in the cache.
  • Your saves are pushed, not polled for. While a machine is connected, the Companion looks over the folder twice a second (stat calls only) and pushes each change straight away. A change of 512 KB or less carries the file itself, so the machine never has to ask for it. A write from the machine is not echoed back to it.
  • Writes go back on close. A file written on the machine is sent when it is closed (or fsync'd), in pieces. The Companion writes it beside the original and swaps it in, so a reader on your computer never sees half a file.
  • The key opens one folder. The machine holds a key made for this project's folder, kept in ~/.reader-companion/mounts/ (0600). It never gets the Companion's token. The socket refuses paths outside the folder, links that lead out of it, and paths the rules say are the machine's own. Unmount forgets the key, which closes every socket that used it.
4. Two modes
  • fuse (Colab and most servers: /dev/fuse and libfuse 2). This is a real mount, and it is lazy: only what is opened is fetched. The first mount on Colab runs pip install fusepy and, as root, apt-get install fuse libfuse2. Allow about a minute for that.
  • mirror (containers that don't allow FUSE). The folder is a real directory that the daemon keeps current both ways over the same socket. Every file is on the machine, but your saves still arrive as you make them, and edits made on the machine go back within a second.

In fuse mode, what was in the folder before the mount is sorted when the mount starts:

  • Copies of your files from earlier pushes are dropped, because the mount is current.
  • The machine's own files (checkpoints, the helpers under .reader/) are kept under the mount.
  • Anything else a run left there is sent back to your computer.

Unmounting puts the machine's own files back in the folder, so copy-before-run works again as it did. A mirror leaves what was there as it was, and sends only what changes after it starts.

5. When your computer sleeps, or is far away

The mount is built so a laptop that sleeps, loses its network, or sits on another continent slows a run down at worst. It never stops one.

  • Everything comes over in the background. After the first archives, the daemon fetches the rest of your files one at a time, smallest first. That covers each file up to 200 MB, and up to 4 GB in all (KOIOS_MOUNT_FILL_FILE_MB, KOIOS_MOUNT_FILL_MB; 0 turns it off). After that the machine reads nothing from your computer, so a sleep mid-run costs nothing for reads.
  • A read that does need your computer waits instead of failing. If a file isn't on the machine yet and your computer can't be reached, the read waits up to 15 minutes for the connection to come back (KOIOS_MOUNT_WAIT_S). The program is held up, not crashed. Listings and file sizes never wait: they come from the tree the machine already has.
  • Writes queue. A file written while your computer is away is kept on the machine, and the program's close() succeeds. The queue is saved on disk, so it survives a restart of the daemon. It is sent as soon as the socket is back, and the daemon redials with backoff. If your computer saved the same file in the meantime, the machine's version wins, and the daemon logs it.
  • Your computer is kept awake while it is mounted. While a machine is connected, the Companion holds the system's own lock against sleep: caffeinate -i -s on macOS, systemd-inhibit on Linux, SetThreadExecutionState on Windows. It lets go when the last machine disconnects. The display can still sleep. A laptop on battery with its lid closed sleeps anyway; nothing a program does changes that, and the three points above cover it. To turn this off, put "keep_awake": false in ~/.reader-companion/config.json.
  • Notebook cells run in the project's folder. While the folder is mounted, the page moves the notebook's kernel into it, quietly, once per kernel: no output, and no cell number used. So import mymodule and relative paths work from a cell as they do from the console.
  • Distance. The first read of a big file costs a round trip through Cloudflare: tens of milliseconds within a region, a few hundred across an ocean. Argo Smart Routing (below) shortens that middle leg. Datasets still belong in the data place (koios_data.path(...)), not in the project folder.
6. A tunnel of your own, with Argo Smart Routing

The Companion's default tunnel is a free quick tunnel. It needs no account, but it gets a new ….trycloudflare.com address at every start and can't use Argo. Argo Smart Routing is Cloudflare's paid routing. It carries traffic between Cloudflare's data centres on the paths it currently measures as fastest. For a mount, that is the leg between the edge near the GPU machine and the edge near your computer. To use it, give the Companion a named tunnel on your own Cloudflare account:

  1. You need a domain on Cloudflare (any plan) with billing set up; Argo is billed per month and per GB.
  2. Create an API token at dash.cloudflare.com → My Profile → API Tokens. It needs these permissions, and can be limited to the one zone: - Account · Cloudflare Tunnel: Edit - Zone · DNS: Edit - Zone · Zone Settings: Edit - Zone · Zone: Read
  3. On the computer with the files:
   reader-companion tunnel setup --hostname koios.example.com --api-token <token>
   reader-companion start            # or reopen the Koios app
   reader-companion tunnel status    # named tunnel, Argo on

Setup does the following through Cloudflare's API:

  • creates (or reuses) a tunnel named koios-<computer id>;
  • points https://koios.example.com at the Companion;
  • adds the DNS record;
  • turns Argo Smart Routing on for the zone;
  • keeps the tunnel's own token in the Companion's settings (0600).

The API token is not saved. The Companion runs cloudflared tunnel run with the tunnel's token in its environment, not on the command line. Mounts then dial the fixed address, so a restart of the Companion no longer changes it.

If Argo can't be turned on (no billing, or a token without Zone Settings: Edit), setup says why and the tunnel works without it. You can turn Argo on later under your domain → Traffic → Argo Smart Routing. reader-companion tunnel quick goes back to quick tunnels.

7. Measuring it over a real tunnel

companion/tests/live_tunnel.py serves a folder and mounts it through a real tunnel, measures it, and prints:

  • how long the mount takes to be ready;
  • a cold and a cached read of a 6 MB file;
  • how long a save takes to reach the other side, each way;
  • the round trip of a read.
cd companion && python3 -m tests.live_tunnel                    # a quick tunnel
KOIOS_LIVE_HOSTNAME=koios.example.com KOIOS_LIVE_TUNNEL_TOKEN=<tunnel token> python3 -m tests.live_tunnel   # yours, with Argo

Both ends run on one computer, but the daemon dials the tunnel's public address, so every byte goes out to Cloudflare and back in. It needs cloudflared to reach Cloudflare's edge: TCP or UDP port 7844 out, and DNS for argotunnel.com. Many CI sandboxes block that; the one this feature was built in did. There, cloudflared was handed a trycloudflare.com address (that request is ordinary HTTPS) but couldn't open the tunnel itself.

Part 2

How it was built, checked and measured

The companion to compute-mount.md, which describes what the mount is and how to use it. This one is the process: what the code did before, the choices made and the ones turned down, how the pieces fit, what each test run found, what was measured and what it showed, which limits belong to the mount and which to the tunnel, and the steps to try it yourself. It is written so that someone who wasn't in the session can retrace the work and check what it claims.

The branch is claude/epic-darwin-18jc7s. docs/compute-mount-process.pdf prints both documents as one PDF; run node scripts/compute-mount-pdf.mjs to print it again.

1. The ask
  1. When I code on my laptop and use Colab's GPU, is the code copied there first? Yes. Section 2 shows how.
  2. Can the connections we already have run the code on that machine without making a whole copy of the codebase there? Yes, by mounting the folder. That is the build.
  3. Can Cloudflare's network make it feel like one device? The mount runs over the Companion's Cloudflare tunnel, keeps one socket open, and pushes changes as they are saved (section 4).
  4. Checkpoints should go where the data is kept. They stay on the GPU machine's disk and go to the data place (section 4.3).
  5. Test it over a real tunnel, handle the limits gracefully, and set up Argo Smart Routing. Sections 6 to 8.

6. What was measured
6.1 Copy against mount, at three simulated distances

companion/tests/bench_mount.py runs both ways on one computer:

  • For the copy, a Jupyter server stands in for the GPU machine, and the copy is koios push (what koios run does before every command).
  • For the mount, the Companion's socket serves the folder and the daemon mounts it with FUSE.
  • Between them sits a proxy that holds every byte back for a fixed time each way, for a round trip of 0, 50 or 150 ms. Those stand in for a machine in the same city, on the same continent, or across an ocean. The proxy limits latency, not bandwidth, and it is not Cloudflare.
  • The project is 300 small Python modules (12 KB each) that a package imports, and a 6 MB file.
  • The raw numbers are in docs/compute-mount-bench.json; run python3 -m tests.bench_mount to measure again.

Figure 7. Before the first run can start. The copy sends all 303 files, and the first one also starts a kernel on the machine. The mount sends the tree and the 302 small files as archives. The copy's 2.2 s at 0 ms includes that machine's first kernel start, which was slower than the later ones.


Figure 8. After editing one file. The copy is koios run's push: connect, compare 303 files, send one. It grows with distance because each command opens a new connection, several round trips. The mount's time is the half-second look on your computer plus one trip, so it barely moves with distance. The bigger difference doesn't show in the chart: with the copy someone has to run it, and with the mount nobody does. At 0 ms the copy is quicker, because the look is on a 0.5 s timer.


Figure 9. The cost the mount adds: importing 300 modules takes about 0.5 to 0.7 s through FUSE, against about 0.2 s from the machine's disk. The files are all cached by then, so the extra is FUSE itself: Python looks up each module in several places, and every lookup is a call into the daemon. The cost doesn't grow with distance (the 150 ms row is the fastest), and it is paid once per process start, not per step of a training loop.

What the numbers don't cover: a real Cloudflare path (its own latency, and its throughput for large reads), Colab's disk, and a laptop on Wi-Fi. Section 6.2 covers the first and the last.

6.2 Over a real Cloudflare tunnel

tests/live_tunnel.py was run on a MacBook Air over Wi-Fi, through a real quick tunnel (contractors-securities-trucks-intro.trycloudflare.com). Both ends ran on the Mac: the Companion's socket served the folder, and the daemon mounted it by dialling the tunnel's public address. So every byte went out to Cloudflare and came back in, crossing the Wi-Fi twice where a Colab run crosses it once. The Mac has no FUSE, so this was the mirror mode, which copies every file first.

The baseline is the same script and mode with no tunnel (KOIOS_LIVE_LOCAL=1 KOIOS_LIVE_MODE=mirror), median of three runs. It ran in the Linux container the feature was built in, not on the Mac. The raw numbers are in docs/compute-mount-live.json.


Figure 10. What the tunnel adds. A save reaches the other side in 0.24 s against 0.22 s without the tunnel, and a write comes back in 0.59 s against 0.46 s. Both times are mostly the mount's own timers (it looks for changes every 0.5 s on your computer and every 0.7 s in the mirror), so the tunnel adds a few hundredths of a second to the first and about a tenth to the second. The first copy is where the tunnel costs: 6.4 MB took 4.8 s, about 1.3 MB/s, against a quarter of a second without it.

What it shows:

  • Edits cross as fast as the mount's own timers allow. The real tunnel barely changes how quickly a save on one side shows on the other.
  • Throughput is the tunnel's cost. 1.3 MB/s is the figure to plan around for the first copy, and this run understates it: the bytes crossed the Mac's Wi-Fi twice. The FUSE mode (Colab) needs it less, because only files of 2 MB or less are sent before the mount is ready, Python files first; everything else follows in the background. For a project with many large files, a named tunnel with Argo (section 6 of compute-mount.md) is where to look.
  • What still needs measuring: a Colab run (FUSE, one crossing), and the round trip and MB/s over the tunnel, which the fixed script now reports.

9. Trying it yourself, step by step
9.1 Before you start
  1. Merge or check out claude/epic-darwin-18jc7s and deploy the site (or run it locally), so the page has the mount switch.
  2. Update the Companion on your laptop to 0.19.0: Settings → Updates, or run the setup line again. reader-companion --version should say 0.19.0.
9.2 The tests on your laptop (10 minutes)
cd companion
git fetch origin && git checkout claude/epic-darwin-18jc7s   # the mount is on this branch until #322 is merged
python3 -m venv .venv && . .venv/bin/activate
pip install -e . fusepy
python3 -m unittest discover -s tests          # 177 tests; FUSE ones skip where there's no /dev/fuse (macOS)
cd .. && npm ci && npx tsc -b && node --test scripts/compute-link.test.mjs scripts/companion.test.mjs

Use python3 (macOS has no python command outside a virtual environment). On macOS, which has no /dev/fuse without macFUSE, the FUSE tests skip and the mirror tests still run. On Linux, sudo apt-get install fuse libfuse2 first.

9.3 A real tunnel, measured (5 minutes)
cd companion
python3 -m tests.live_tunnel --save ~/koios-live.json

Expect a trycloudflare.com address within about 10 s. The script then waits for the new name to resolve and says so every few seconds; this can take a minute. Then come "mounted" and these lines:

  • 6 MB cold / cached (FUSE only): the cold read is your trip to Cloudflare and back, twice.
  • save here → there: about 0.25 s (section 6.2).
  • write there → here: about 0.6 s in the mirror; with FUSE, by the time the file is closed.
  • round trip of a small request in milliseconds, and MB/s for a 6 MB file through the tunnel.

If it gives up waiting for the name, your computer has cached "no such name" from its first look. On a Mac, run sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder, then run it again; each run gets a new address. For a baseline without the tunnel on the same computer: KOIOS_LIVE_LOCAL=1 python3 -m tests.live_tunnel.

9.4 The mount on Colab (15 minutes)
  1. Open a project whose files are on your laptop (Storage & compute → Move files here if they aren't), with its code on Colab, and connect a GPU runtime.
  2. Storage & compute → Sync → tick Mount the folder on Colab. The first time, wait about a minute while fusepy installs. The bar should then read Mounted on Colab ⇄ live.
  3. In the compute's terminal: ls /content/playgrounds/*/ shows your files, and mount | grep koios shows the FUSE mount.
  4. Edit a .py file on your laptop and save it. Within about a second, cat it on Colab.
  5. In a notebook cell: import os; os.getcwd() should be the project's folder, and import yourmodule should work.
  6. Run something that writes results/x.json and checkpoints/model.pt. The JSON appears on your laptop; the checkpoint doesn't, and turns up in Drive under Koios/Data/<project>/ a few seconds later.
  7. On macOS, while it is mounted, pmset -g assertions | grep caffeinate shows the Companion holding sleep off.
  8. Turn Wi-Fi off for a minute and keep running. Reads go on, and a file written meanwhile appears on your laptop once Wi-Fi is back. cat ~/.koios-mount/*/status.json on Colab shows awaySince and waitingToWrite.
  9. Untick the switch. The bar goes back to Send code, and runs copy again.
9.5 Argo Smart Routing (20 minutes, needs a Cloudflare account)
  1. Add a domain to Cloudflare, and set up billing if you want Argo.
  2. Make an API token with: Account · Cloudflare Tunnel: Edit; Zone · DNS: Edit; Zone · Zone Settings: Edit; Zone · Zone: Read.
  3. reader-companion tunnel setup --hostname koios.yourdomain.com --api-token <token>, then reader-companion start.
  4. reader-companion tunnel status should say "named tunnel … Argo Smart Routing on".
  5. Measure again with your tunnel, and compare with 9.3:
   KOIOS_LIVE_HOSTNAME=koios.yourdomain.com KOIOS_LIVE_TUNNEL_TOKEN=<from ~/.reader-companion/config.json> python3 -m tests.live_tunnel
  1. If you decide Argo isn't worth what it costs, turn it off under the domain → Traffic → Argo Smart Routing, or run reader-companion tunnel quick to go back to quick tunnels.
